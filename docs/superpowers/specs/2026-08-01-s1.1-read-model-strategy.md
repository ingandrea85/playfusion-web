# S1.1 — Read-model strategy (event projection vs per-BC query)

- **Date:** 2026-08-01
- **Slice:** S1 — Read models / query endpoints
- **Issue:** [ingandrea85/playfusion-web#15](https://github.com/ingandrea85/playfusion-web/issues/15)
- **ADR:** ADR-002 (REST + API Gateway + mono-Lambda per BC, modular monolith), ADR-011 (Unified 2.0 monorepo)
- **Blueprint:** D-O5-1 (per-category registration cap)
- **Branch:** `feature/s1-read-models`

## Question

Slice S1 exposes the read side of the Bundle Enrollment flow — the query endpoints
that feed the E1 organizer dashboard and the E3 public landing (S4/S5):

- **S1.2** `GET /events` (list per org) + `GET /events/:id` (detail + categories) — O3
- **S1.3** `GET /events/:id/registrations?state=` — O5
- **S1.4** registration-window state + remaining capacity per category — O5

How should these reads be served: a dedicated **read model** projected from Domain
Events (CQRS), or a **direct query** against each Bounded Context's own current-state
store?

## Decision

**Serve reads by querying each Bounded Context's own current-state store directly.**
Add a Global Secondary Index per new access pattern. Do **not** introduce a separate
event-sourced projection store, projection consumer, or denormalized read database.

Concretely for S1:

| Read | BC | Store / access pattern |
|---|---|---|
| list events per org | O3 | `o3-events` + new `org-index` GSI (`organizationId` HASH) |
| event detail | O3 | `o3-events` `GetItem` by `sportEventId` |
| registrations by event (+state) | O5 | `o5-registrations` + new `event-index` GSI (`sportEventId` HASH), `status` filter |
| window state + per-category capacity | O5 | `o5-windows` (state + caps) + `o5-registrations` `event-index` (active counts) |

### Cross-BC data: denormalize on the write side, never join on the read path

The per-category cap (D-O5-1) is conceptually an attribute of the event's categories,
which O3 owns. But O5 is the authority for *"can this category still take a
registration"*, and BC autonomy (ADR-002) forbids a synchronous O5→O3 call on the
query path. So the cap is **denormalized into O5's registration-window** when
registrations are opened (`open-window` accepts `capacities: { categoria: max }`). S1.4
then computes `remaining = cap − activeCount` entirely inside O5 — no query-time
cross-BC read. This mirrors how O5 already denormalizes participant existence into its
own directory from `ParticipantCreated` events.

Likewise `organizationId` is **denormalized onto the O3 event item at write time** (it
already flows in on `x-organization-id` and into the `EventPublished` envelope; S1.2
persists it on the item too) so list-per-org is a single-BC GSI query.

## Rationale

- **Matches the runtime we already have.** The migrated pilot persists current-state
  aggregates per BC in DynamoDB. There is no event store to replay; "event sourcing"
  here would mean *building* one purely to serve reads.
- **A projection store buys nothing at this scale and adds real cost:** a new consumer,
  a new table, eventual-consistency lag between write and read, and idempotency
  handling — for endpoints that are simple current-state lookups scoped to one BC.
- **ADR-002 (modular monolith) favours the simplest thing that keeps BCs autonomous.**
  Per-BC direct query with write-side denormalization keeps every S1 endpoint
  single-BC and dependency-free on the read path.
- **Reversible.** If a future read needs a genuine cross-BC materialized view (e.g. a
  tenant-wide analytics dashboard), a projection consumer can be added *for that view*
  without disturbing these endpoints. We are not foreclosing CQRS; we are declining to
  pay for it before a read actually needs it.

## Consequences

- New GSIs land in **both** `infra/cdk/lib/data-stack.ts` (deployed) and
  `scripts/provision.ts` (LocalStack) so local and deployed topologies stay in lockstep.
- `open-window` gains an optional `capacities` map; the write that populates it in the
  UI is S4.3 ("Open registrations — per-category cap"). S1 ships the read + the storage
  shape; a window opened without caps simply reports no capacity ceiling.
- Reads follow the same hexagonal seam as writes (repository port + adapter) in O5, and
  a matching thin read-store port in O3, so query logic is unit-testable with in-memory
  fakes — no LocalStack required for the S1 test suite.
